## 1. 제품 한 줄

괴짜 방송국의 정체불명 타워 쇼에 참가해 짧은 도전을 연속으로 돌파하고, 강한 조합을 만들며, 방송과 진행자의 비밀을 밝혀내는 세로형 모바일 액션 퍼즐이다.

## 2. 이번 프로토타입의 성공 조건

첫 프로토타입은 15층 한 판이 처음부터 끝까지 자동 진행되며 다음 감각을 수치와 로그로 증명해야 한다.

1. 규칙은 설명 없이도 빠르게 이해된다.
2. 한 층이 짧고 다음 층을 바로 해보고 싶다.
3. 콤보와 Quirk 조합이 눈에 띄게 강해지는 순간을 만든다.
4. 실패해도 체크포인트와 짧은 재도전 때문에 답답하지 않다.
5. 진행 중 방송 사고와 진행자 대사로 다음 비밀이 궁금해진다.
6. 광고 시청과 결제는 같은 게임 내 이점을 같은 제한으로 제공한다.

이번 단계는 실제 손맛, 최종 그래픽, 네이티브 광고, 온라인 랭킹을 완성했다고 주장하지 않는다.

## 3. 범위

### 포함

- 15층으로 끝나는 한 개의 런
- 마이크로게임 3종
  - Timing Ring: 정해진 구간에 맞춰 입력
  - Tap Panic: 제한 시간 동안 목표 횟수 달성
  - Drag Dodge: 위험 구간을 피해 목표 지점 도달
- Quirk 4종과 선택·중첩 효과
- 하트, 콤보, 점수, 체크포인트
- 진행자 대사, 방송 자막, 짧은 스토리 비트
- Sponsor Boost 한 종류의 효과와 제한을 시뮬레이션
- 고정 시드 기반 자동 플레이 및 대량 밸런스 시뮬레이션
- 구조·파일 크기·의존성 자동 검사

### 제외

- Quirky Ball의 합치기 물리, 폭탄, 조커를 그대로 이식
- 최종 UI와 아트
- Supabase 실연동
- AdMob과 스토어 결제 실연동
- 실시간 친구 네트워크
- 라이브 서비스용 운영 도구
- 15층 이후 콘텐츠 양산

제외 항목은 현재 프로토타입이 재미와 구조를 통과한 뒤에만 추가한다.

## 4. 핵심 게임 흐름

```text
런 시작
  -> 층 도전 선택/배정
  -> 마이크로게임 결과 계산
  -> 성공: 점수·콤보·스토리 진행
  -> 실패: 하트 또는 보호 효과 소모
  -> 일정 층: Quirk 선택
  -> 체크포인트 저장
  -> 15층 피날레
  -> 런 결과와 발견한 비밀 출력
```

각 층은 `준비 -> 도전 -> 판정 -> 보상/손실 -> 다음 층`이라는 한 가지 공통 상태 흐름을 쓴다. 마이크로게임은 판정 규칙만 제공하며 런 진행을 직접 제어하지 않는다.

## 5. 재미와 카타르시스

시뮬레이션처럼 보이지 않게 만드는 핵심은 숫자 증가 자체가 아니라 짧은 결단과 즉각적인 결과다.

- 한 도전은 수 초 안에 결과가 난다.
- 연속 성공은 점수뿐 아니라 다음 도전을 유리하게 바꾼다.
- Quirk는 미세한 수치 보정보다 플레이 규칙을 눈에 띄게 바꾼다.
- 실패 직후 긴 대기나 전체 초기화 대신 짧은 회복 경로를 둔다.
- 5층 단위로 강한 사건과 연출 지점을 배치한다.

초기 Quirk 4종은 최소 조합 검증용이다.

| Quirk | 효과 방향 | 검증 목적 |
|---|---|---|
| 넓은 판정 | 성공 구간 확대 | 안정성 선택 |
| 과열 콤보 | 콤보 배수 증가, 실패 손실 증가 | 위험·보상 선택 |
| 재방송 | 한 번의 실패를 재시도 | 회복 선택 |
| 변칙 편성 | 다음 도전 교체 또는 유리한 유형 우선 | 경로 선택 |

수치는 데이터 파일에서 바꾸며 코드에 흩뿌리지 않는다.

## 6. 스토리 구조

겉으로는 가볍고 빠른 방송 쇼지만, 오를수록 방송국과 진행자의 이상한 흔적이 드러난다.

- 1~4층: 참가자와 규칙 소개, 코미디 중심
- 5층: 첫 방송 사고
- 6~9층: 대사와 자막의 모순
- 10층: 진행자가 숨기는 단서
- 11~14층: 타워 쇼의 목적에 대한 의심
- 15층: 첫 피날레와 다음 런을 유도하는 비밀 공개

스토리는 플레이를 멈추는 긴 컷신보다 한두 줄 대사, 방송 자막, 결과 화면의 변화로 전달한다. 헤드리스 단계에서는 이벤트 ID와 텍스트 로그로 순서와 빈도를 검증한다.

## 7. BM 원칙

Pay-to-win 요소를 허용한다. 다만 같은 게임 내 이점은 광고 시청으로도 얻을 수 있고, 결제와 광고 모두 같은 사용 제한을 적용한다.

### 초기 모델: 제한형 Pay-or-Watch

- 한 런에 Sponsor Boost 1회
- 초기 일일 한도 5회
- 보상형 광고 1회 또는 유료 티켓 1개로 같은 Boost 제공
- 광고 제거 상품 보유자는 광고 없이 같은 Boost를 받지만 한도는 동일
- Boost 후보
  - 하트 +1
  - 실패 보호 1회
  - 성공 판정 구간 확대
  - Quirk 선택지 2개에서 3개로 증가
  - 피날레 제한 시간 완화

결제자가 랭킹에서 분리되지는 않는다. 서버에는 검증과 밸런싱을 위해 Boost 사용 여부만 기록하며, 정상적인 광고·결제 Boost를 랭킹 제외 사유로 사용하지 않는다.

실제 결제와 광고 SDK는 헤드리스 프로토타입에 넣지 않는다. 프로토타입은 동일 효과와 동일 제한이 적용되는지만 검증한다.

## 8. 랭킹과 국가/소속

랭킹은 공식/비공식 또는 무과금/지원 사용으로 나누지 않는다. 디버그, 치트, 불가능한 결과만 검증 단계에서 제외한다.

### 국가/소속은 단일 선택값

Quirky Ball의 실제 구조를 따른다.

- 사용자는 일반 국가와 유머성 특수 소속이 함께 있는 하나의 목록에서 정확히 하나를 고른다.
- 예: 대한민국, 독일, 외계인, 그림자정부, 렙틸리언
- 국가와 소속을 별도 필드나 별도 카테고리로 만들지 않는다.
- 내부 저장은 Quirky Ball과 호환하기 쉬운 단일 코드 필드 `country`를 사용한다.
- UI 문구는 오해가 없도록 항상 `국가/소속`으로 표시한다.
- 같은 코드는 프로필 표시와 국가/소속 랭킹 그룹에 함께 사용한다.

### 랭킹 보기

- 전체
- 국가/소속
- 친구

타임어택은 별도 경기 방식 또는 지표이며, 필요할 때 그 안에서도 동일하게 전체·국가/소속·친구 보기를 쓴다. 첫 헤드리스 프로토타입은 점수와 완주 시간 산출까지만 만들고 온라인 조회는 뒤로 미룬다.

## 9. 구조

하나의 Godot 프로젝트 안에서 런 규칙과 화면을 분리한다.

```text
assets/
data/
  gameplay/
  story/
  economy/
  localization/
scripts/
  core/
    run/
    challenges/
    quirks/
    story/
    economy/
    simulation/
  gameplay/
  ui/
  services/
  house_duck/
    ui/
    platform/
    data/
scenes/
  gameplay/
  ui/
  qa/
resources/
  themes/AppTheme.tres
scripts_dev/
  qa/headless/
  qa/captures/
  tools/
docs/
  canonical/
  superpowers/specs/
  history/
```

### 의존성 규칙

- `scripts/core`는 Node, 화면, 광고, 결제, Supabase를 참조하지 않는다.
- `gameplay`는 core 결과를 Godot 장면과 입력에 연결한다.
- `ui`는 상태를 표시하고 명령을 전달할 뿐 게임 규칙을 계산하지 않는다.
- `services`는 저장, 광고, 결제, 백엔드의 경계다.
- `house_duck`에는 실제로 두 게임에서 재사용되는 코드만 둔다.
- 한 게임에서만 쓰이는 코드를 미래 공용화 목적으로 미리 추상화하지 않는다.

핵심 데이터 흐름은 `입력/봇 명령 -> core 판정 -> RunState 변경 -> 이벤트 -> UI/로그` 한 방향으로 유지한다.

## 10. UI 공통규칙

UI 구현 단계에서는 한 값을 바꾸면 전체 화면에 반영되도록 세 층만 둔다.

1. `AppTheme.tres`: 폰트, 기본 색, 컨트롤 스타일
2. `DesignTokens`: 간격, 반경, 색 역할, 글자 크기, 애니메이션 시간
3. 공통 컴포넌트: 버튼, 카드, 팝업, 탭, 칩, 랭킹 행

개별 화면은 직접 색상·글자 크기·모서리 값을 가지지 않는다. 예외는 이유와 만료 조건이 있는 경우만 허용한다. Quirky Ball의 공통 UI는 그대로 복사하지 않고, 실제 재사용 가능 부분만 확인해 작은 단위로 가져온다.

헤드리스 단계에서는 UI 파일을 양산하지 않는다. 토큰 계약과 향후 공통 컴포넌트 경계만 고정한다.

## 11. 큰 파일 방지

### 파일 크기 기준

- `.gd`: 500줄 경고, 800줄 초과 실패
- `.md`: 600줄 경고, 1200줄 초과 실패
- 생성물, 번역 원본, 외부 `addons`는 명시적 예외 목록으로 관리

줄 수만 맞추려고 의미 없는 파일 분할을 하지 않는다. 한 파일이 두 가지 이상의 변경 이유를 가지거나, 기준을 넘을 때 책임 단위로 나눈다.

### 문서 분리

`docs/canonical/README.md`를 현재 문서의 짧은 색인으로 두고 다음 주제로 나눈다.

- product
- gameplay
- story
- economy
- architecture
- design_policy
- qa
- work_state

완료된 긴 기록은 `docs/history`로 옮긴다. 현재 규칙과 과거 작업 로그를 같은 문서에 계속 누적하지 않는다.

### 자동 검사

한 개의 구조 검사 명령이 다음을 확인한다.

- 파일 크기 한도
- core의 UI·광고·결제·Supabase 참조 금지
- 문서 색인의 끊어진 링크
- 데이터 파일 파싱 가능 여부

별도 검사 도구를 여러 개 만들지 않고 한 진입점에서 실행한다.

## 12. Godot 도구와 플러그인

### 바로 적용할 후보

- Godot 공식 Asset Library에 배포된 원본 `Godot MCP/CLI 0.7.2`
  - Godot Foundation 제작 플러그인은 아니며 Community 항목이다.
  - 제3자 개조본 대신 공식 배포 채널의 upstream 원본을 수정 없이 사용한다.
  - localhost와 프로젝트 경로 제한을 유지한다.
- Context7
  - Godot와 외부 라이브러리 문서를 필요할 때만 조회한다.
- Godot용 개발 skill
  - 설치 전에 저장소와 지시문을 검토하고, 프로젝트 범위를 넘는 동작이 없는 원본만 사용한다.

### 나중에 적용

- 상태 차트: 실제 화면 상태가 복잡해질 때만
- Supabase, AdMob, Billing: 백엔드·수익화 연결 단계
- GUT 등 추가 테스트 프레임워크: 현재 최소 헤드리스 검사로 감당되지 않을 때만

플러그인은 생산성을 입증해야 유지한다. 같은 기능이 Godot 기본 기능과 짧은 스크립트로 충분하면 추가하지 않는다.

## 13. 헤드리스 검증

Godot headless 실행은 고정 시드 한 판과 대량 시뮬레이션 두 종류를 제공한다.

### 고정 시드 스모크

- 15층 완주 또는 명시적 게임오버
- 상태 전이 순서 검사
- 같은 시드는 같은 결과
- Quirk 적용 전후 결과 차이
- 체크포인트 복원 후 결과 일치
- Sponsor Boost 광고 경로와 결제 경로의 효과 동일
- 일반 국가와 특수 소속 코드가 같은 필드와 그룹 규칙을 사용

### 대량 시뮬레이션

초기에는 10,000런을 실행해 다음을 출력한다.

- 층별 도달률
- 평균 런 시간 추정치
- 마이크로게임별 성공률
- Quirk 선택률과 승률
- 콤보 분포
- Boost 사용 전후 완주율
- 특정 시드의 무한 루프 또는 불가능 상태

수치가 목표에 맞지 않으면 데이터 값을 조정한다. 구조를 다시 짜기 전에 실제 분포로 문제를 확인한다.

## 14. 오류 처리

- 잘못된 데이터는 시작 시 파일 경로와 필드명을 포함해 실패한다.
- 알 수 없는 도전, Quirk, 스토리 이벤트 ID는 조용히 무시하지 않는다.
- 저장 데이터는 버전을 가진다.
- 체크포인트 쓰기는 임시 파일 후 교체 방식으로 손상 위험을 줄인다.
- 온라인 서비스 실패는 core 진행을 깨지 않고 서비스 계층에서 재시도 또는 보류한다.
- 광고나 결제 성공 여부는 클라이언트 임의 값만으로 확정하지 않는다.

## 15. 구현 순서

1. 프로젝트 규칙, 폴더, 구조 검사
2. 순수 데이터 모델과 RunState
3. 공통 도전 인터페이스 없이 필요한 3개 판정 함수
4. 층 진행, 하트, 콤보, 체크포인트
5. Quirk 4종
6. 스토리 이벤트 로그
7. Sponsor Boost 동등성
8. 국가/소속 단일 코드와 랭킹 집계용 결과 모델
9. 고정 시드 스모크와 10,000런 시뮬레이션
10. 결과 검토 후 최소 플레이 화면

한 단계는 실행 가능한 검사와 함께 끝낸다. 프로토타입 결과가 재미 기준을 통과하기 전에는 콘텐츠 수와 플러그인 수를 늘리지 않는다.

## 16. 승인된 핵심 결정

- 첫 단계는 headless다.
- 15층·3도전·4 Quirk로 범위를 제한한다.
- 이야기는 괴짜 방송국 타워 쇼의 코믹 미스터리다.
- Pay-to-win을 허용하며 광고와 결제는 같은 이점을 제공한다.
- 지원 사용자는 랭킹에서 분리하지 않는다.
- 국가와 유머성 소속은 하나의 `국가/소속` 선택 목록과 단일 코드다.
- UI는 Theme, Token, 공통 컴포넌트로 일괄 변경 가능하게 만든다.
- 큰 파일과 잘못된 core 의존성은 자동 검사한다.
- House Duck의 개조 Godot MCP는 가져오지 않고 공식 배포 채널의 upstream 원본만 검토·적용한다.
